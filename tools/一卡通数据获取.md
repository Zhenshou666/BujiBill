# 校园一卡通数据怎么拿（已跑通，2026-11-17 实测）

平台：<http://etcard.hzcu.edu.cn:8088/easytong_webapp/index.html#/bill>

## 实测结论

| 项 | 结论 |
|---|---|
| 有导出按钮吗 | **没有** |
| 列表页有商户名吗 | **没有**，只有「日期 / 消费 / 金额 / 时间」 |
| 详情页有商户名吗 | **有**：钱包名称、消费终端、商户名称、交易时间、交易单位 |
| 能否抓 HTML | 不行，Vue 单页应用，HTML 里只有一个空 `<div id=app>` |
| 后端接口 | **有，而且列表接口直接返回商户名** |

关键发现：**列表接口 `GetDealRec` 的响应里 `businessName` 就是商户名**，
前端只是没在列表上渲染。所以根本不用逐条点详情。

## 接口清单

| 接口 | 用途 |
|---|---|
| `POST /easytong_app/GetDealRec` | 交易记录列表（含商户名、流水号） |
| `POST /easytong_app/GetConsumptionDetail` | 单笔详情（列表已够用，一般不用调） |
| `POST /easytong_app/GetDealSum` | 收支汇总 |
| `POST /easytong_app/GetTransTypeFeeNum` | 各类型笔数 |
| `POST /easytong_app/GetWalletMoney` | 钱包余额 |

`GetDealRec` 请求体：

```
AccNum=407301&BeginRecNum=1&CardAccNum=-1&Count=20&EPID=0
&TypeNum=-1&WalletNum=0&Time=20261117155112&Sign=xxxxxxxx
```

- `BeginRecNum` + `Count` 是分页（每页 20 条）
- **`Sign` 是签名**，改参数过不了校验，所以不能直接拼 URL 调

响应结构：

```json
{"code":1, "count":210, "list":[
  {"month":"202611", "dealDetail":[
    {"businessName":"...商户名...", "dealDate":"17日", "dealTime":"11:35:16",
     "feeNumStr":"消费", "money":-14.05, "monDeal":"-14.05元",
     "payRecNum":36862110, "unitStr":"元"}
  ]}
]}
```

`payRecNum` 是流水号，拿它当唯一键去重。

## 绕过签名：让页面自己发请求

不逆向 `Sign`，改成**驱动页面滚动**触发无限加载，页面自己会把请求签好发出去，
我们只从抓包缓冲里收响应。这就是 `tools/campus_pull.py` 干的事。

```bash
# 1. 浏览器登录一卡通，停在账单页
# 2. 建会话（假设 id 是 xxxx）
bsk open "http://etcard.hzcu.edu.cn:8088/easytong_webapp/index.html#/bill"
bsk debug start --session xxxx --name campus
# 3. 抓取
python tools/campus_pull.py xxxx
```

⚠️ 响应体在缓冲里**会被淘汰**，必须边滚边取；脚本已经是逐页即时拉取。

## 实际拉到什么

- **84 笔**，时间范围 `2026-10-17 18:49:28` → `2026-11-17 11:35:16`
  （与微信 / 支付宝的导出区间完全对齐，便于三源核对）
- 类型：**80 笔消费（金额为负）+ 4 笔充值（金额为正）**，符号完全对得上
- 商户去重后 **6 个**，全部能归到「餐饮」和「日用」

⚠️ 接口 `count` 返回 210，但当前「本月」筛选只有 84 笔。
210 应该是账户全部历史，要更多就往时间下拉里换范围再跑一次脚本。

## 最大的坑：充值类型名不含「充值」二字

一卡通平台把「微信/支付宝充进校园卡」记为 **`第三方支付平台转账`**。

如果按字面当普通消费处理，就会和微信/支付宝那边的付款**重复计一次支出**。
`campus_pull.py` 已经把它映射成「交易类型=充值」，
`billkit/dedupe.py` 再判成内部转账剔除。

真实数据验证：4 笔充值全部正确落入「内部转账」，没有被算进消费。

## 复用

每月导出一次即可：重新登录 → `bsk debug start` → 跑脚本。
输出覆盖写入 `data/campus/校园卡流水_真实.csv`，
`CampusAdapter` 直接可读（列名已对齐：交易时间 / 交易类型 / 商户名称 / 交易金额 / 余额）。

# 产品化：让程序自己也能拿到数据

`campus_pull.py` 依赖 browser-skill 的抓包缓冲，**这是智能体才有的特权，程序没有**。
真实用户装上「账单助手」后，只能点按钮、开网页。

所以把同一套逻辑改写成**一段跑在用户浏览器里的脚本**：`tools/campus_grab.js`。

| 路线 | 用户操作 | 代价 | 结论 |
|---|---|---|---|
| 程序直接调接口 | 无感 | 被 `Sign` 拦住，要逆向混淆 JS，签名一变就废 | ✗ |
| 内置 Playwright | 输入账号密码 | 带 150MB Chromium，验证码难搞 | 太重 |
| **浏览器内脚本（已采用）** | 每月粘一次脚本 | 无 | ✓ |
| 截图 OCR | 拍照上传 | 列表页无商户名，等于白干 | ✗ |

脚本做的事和 `campus_pull.py` 完全一样：hook `fetch`/`XHR` → 自动滚动 →
收集 `GetDealRec` 响应 → 按 `payRecNum` 去重 → 生成 CSV 并触发下载。

已内置到程序：「🎓 校园卡」页有「点开复制脚本」，粘进控制台即可，
下载的 CSV 直接拖回同一个页面入库。

## 脚本的已知边界（含实测结论）

1. **首屏一定会缺，且刷新救不回来**。
   钩子是页面加载完之后才装上的，而首屏 `GetDealRec` 在页面加载后 1 秒内就发出去了；
   粘贴 200 行脚本要 1~2 秒，**永远慢一步**。
   实测：不干预 → 65 笔（缺最新 19 笔）；F5 后立刻粘贴 → 仍然 65 笔。
2. **确定性解法：手动切一次筛选**。
   点顶部「钱包」→ 点回「全部」，列表会重新从 `BeginRecNum=1` 请求，
   此时钩子已装好，首屏必然抓到。脚本会给出提示并等待 30 秒自动接续。
   **实测：85 笔，与完整版对比缺 0 笔**（还多出 1 笔 bsk 抓取之后才产生的充值）。
3. **签名不碰**：脚本从不构造请求，只被动接收页面自己发的响应，`Sign` 问题天然不存在。
4. **累积不重复**：按 `payRecNum` 去重，可反复执行 `__campusGrabAgain()` 直到补齐。
5. **自证完整**：导出时打印「最新一笔」时间，与页面顶端那笔对比即可判断。
   注意不能拿接口的 `count` 当基准——它返回的是账户全部历史（210），
   而当前筛选（本月）可能只有 84 笔，数量对不上是正常的。

## 两条路的关系

| 用途 | 工具 | 前提 |
|---|---|---|
| 本次拿真实数据 | `campus_pull.py`（抓包缓冲） | 需要 browser-skill 会话 |
| 交付给真实用户 | `campus_grab.js`（浏览器内脚本） | 只要能开 F12 |
